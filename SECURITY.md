# Security

This is an unpublished development project. There are no released versions, supported-version guarantees or established security response team. No security contact, private reporting channel or response-time commitment has been verified.

If you discover a vulnerability, keep secrets and exploit details private, stop affected local execution, and prepare a sanitized reproduction. Ask the actual project owner for a verified private reporting route before sending details. Do not put credentials or an undisclosed exploit in public issue forms. Once a hosted repository exists, its owner must establish a private reporting route before release.

## Controls

- Strict configuration/skill/checkpoint schemas; unknown configuration keys rejected.
- Project-relative storage, traversal and symlink checks, private data modes and atomic JSON replacement.
- Checkpoints contain explicit text only; recognizable credentials are redacted. No environment/source collection or telemetry.
- Skills are declarative data; parsing them does not execute their contents.
- Process checks require policy permission plus per-invocation approval, with argument arrays, bounded output, timeouts and cancellation.
- Offline commands make no provider requests. Explicit model/connection requests require configuration permission and invocation approval; provider URLs reject credentials and redirects, and response time/size are bounded.

These controls are not a sandbox. Approved executables run with OS user privileges and may read files or access the network. Redaction is best effort and cannot recognize every secret; do not put secrets in prompts, config, command arguments or checkpoints. Path checks reject known symlinks but cannot prevent a concurrent local attacker from replacing ancestor directories between checks. Use a trusted workspace and OS isolation for hostile content.

Graph results are heuristics. The scanner excludes common secret/generated directories, but filenames themselves can be sensitive. Review reports before sharing. Package installation and `npm audit` contact the registry; that is development tooling, not product telemetry.

Run `npm audit` and review changes to the lockfile. See [security boundaries](docs/architecture/security-boundaries.md).

On POSIX, termination targets the spawned process group. Deliberately detached descendants can escape that group and outlive the check; output-pipe closure prevents them from keeping the report pending. On Windows only the direct child is terminated. Use OS isolation for full process-tree containment.

Optional model requests send the explicit task, any selected output schema, and the configured authentication header to the chosen endpoint. No files or checkpoints are attached implicitly. Custom HTTPS endpoints may receive that provider credential; verify endpoint ownership before approval. Client cancellation does not guarantee a remote job stopped or that no charge occurred. Provider error bodies are omitted. See [provider setup](docs/integrations/providers.md).

Streaming text is provisional and line-buffered for sanitization; structured deltas are withheld until validation. Output schemas use a bounded allowlist with no remote refs, regex or implicit coercion. Raw JSON is validated, redacted as data, then revalidated; no invalid structured payload is returned as valid. Schemas themselves are sent to the provider, so keep sensitive field names, descriptions and enum values out of them.

Client function calls grant no execution rights. The separate executor requires explicit approval for an immutable, one-use batch. CLI execution also requires `permissions.allowTools=true`, `--execute` and the exact approval ID typed on a terminal; piped input cannot approve. The fixed verification tool also requires process permission and displays resolved configuration-owned command/arguments. Every subsequent batch requires fresh approval. Calls and resolved effects containing recognizable secrets are rejected rather than approved with hidden/mutated arguments. Approval authorizes sending sanitized tool results to the chosen provider. In-memory host handlers must honor cancellation; synchronous or uncooperative JavaScript cannot be preempted. See [tool invocation](docs/integrations/tool-invocation.md).

Streaming tool arguments and native reasoning are private reconstruction state. Only a complete, validated turn after clean stream termination can reach approval. Truncation, terminal disagreement, trailing errors and early iterator return cannot trigger tools. Provisional text can appear before a stream fails and must not be treated as a completed result. Streaming uses the same network and exact-batch execution approvals as ordinary tool turns.

Combined tool/output schemas govern final answers independently of tool argument schemas. Invalid final JSON or schema mismatches are withheld; structured streams expose no partial JSON. Tool-looking fields inside final JSON do not grant execution rights. A final validation failure closes the session and does not rerun previously approved tools; prior effects cannot be rolled back by validation. The exact validated/redacted final object is serialized directly, avoiding changes after schema validation.

Tool-result schemas are local validation policy, separate from provider-visible argument and final-answer schemas. Every successful schema-bound result must validate before and after data redaction, including selected-credential redaction at the adapter boundary. Invalid JSON, schema mismatch or a sensitive property name withholds the result and prevents follow-up. An executor validation failure stops later handlers in that batch; its consumed approval cannot be retried. The session independently applies the selected credential after the approved batch finishes, so a failure detected only there cannot prevent earlier effects. Already completed effects cannot be rolled back. Handler exceptions produce a fixed generic `isError` result, never exception details or a claimed successful value. Schemas are part of the immutable approval review; overriding them grants no execution rights.

Project search/read require exact batch approval even though they are read-only. Their argument validators reject unsafe paths and out-of-range limits before approval. Approved execution honors layered `.gitignore`, fixed credential/generated exclusions, strict UTF-8, regular-file/link checks and finite read/result budgets. Ignore rules that cannot safely be loaded fail closed. File contents and filenames are untrusted data; instructions in them cannot grant permission. Exclusions/redaction are best effort, not secret discovery. Review the [file policy](docs/integrations/project-files.md) before sharing source.

`task --with-context` explicitly authorizes sending the current checkpoint; it is omitted by default and encoded as untrusted JSON reference material. The total deadline also covers approval waits. Denial, cancellation or late approval cannot start a new batch. Failure reports retain only bounded safely emitted text; unvalidated structured text is withheld, including pending tool commentary and length/refusal fragments. Ordinary JSON and stream transports reject invalid UTF-8. Validated final JSON is delivered without a subsequent string rewrite. Use a trusted project root: concurrent hostile directory replacement and arbitrary approved subprocess effects still require OS isolation.

Read-only [Git tools](docs/integrations/git-inspection.md) require exact approval and process permission. Fixed argv and a sanitized environment disable configured execution hooks/filters, external diffs, prompts and optional locks. Unsafe metadata, shared object stores, configuration includes, partial clones and linked worktrees fail closed. Diff reads require one existing file under project policy; they never accept arbitrary revisions or flags. Process and result budgets, cancellation and root validation apply before returning data.

[Edit previews](docs/integrations/project-edits.md) fully read the selected existing file after approval, require exact replacement/patch matches and return a complete bounded diff. Proposals are short lived and scoped to one registry, with a new approval required for application. Write permission defaults false. The Node backend cannot guarantee an atomic version check plus replacement against external writers, so application is unavailable before any write; stale bytes/identity report conflict. No cooperative-lock override or automatically executed edited code exists. Configuration and ignore-policy targets are protected. Secret detection remains best effort; do not authorize disclosure of sensitive source.

[Built-in orchestration](docs/features/orchestration.md) defaults disabled and snapshots roles/configuration/permissions before the first request. Planner output cannot grant authority; worker tools are fixed, scope checked and subject to central serialized exact approval. Workers have no delegation or arbitrary configured-process tool. At most two workers run with finite task/depth/context/output/deadline budgets. Overlaps and out-of-scope path claims are surfaced for review, never automatically merged. Reports of completion remain untrusted model claims. No external coding-host integration, operating-system sandbox or billing budget is implied.

## Audit hardening and remaining boundaries

JSON storage, skill metadata, graph source and `.gitignore` policy reads reject hard links to prevent reading an outside inode through an inside name. Bounded read loops handle legal short reads; identity/timestamp checks detect in-place changes. JSON and skill metadata reject malformed UTF-8. Failed JSON writes or syncs clean temporary files without replacing the prior target. These measures do not make approved subprocesses sandboxed or guarantee persistence after power loss; directory metadata is not fsynced.

Model IDs reject C0, DEL and C1 controls before normalization, including role overrides, so they cannot inject terminal controls into approval labels. Runtime/config/status diagnostics sanitize explicitly configured provider credentials even for short values or custom environment names. Credential-bearing property names and typed scalar JSON values are withheld rather than changing their schema types. Truncated private-key blocks are redacted through end-of-output. Redaction cannot recognize unknown private data; inspect reports before sharing.

The repository uses private package metadata, least-privilege pinned-action workflows and deterministic provider fixtures. No workflow requires live provider secrets. The Windows job is installation/type coverage only; POSIX terminal tests and process-group guarantees do not establish full Windows support. Local hygiene scans are heuristic and do not replace review or a dedicated secret scanner before distribution.

Regular-file readers open nonblocking before descriptor type checks, preventing POSIX named pipes from stalling configuration/skill/graph operations. The checked-in config schema rejects model control characters too; semantic endpoint checks still require the runtime validator.
